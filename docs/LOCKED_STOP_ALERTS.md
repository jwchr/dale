# Stop alerts while the phone is locked (#176 step C): design

Status: code built in #192, not yet deployed. Where the build differs from the design text, this page now describes what was built ("As built" below and the notes in each step). Steps A and B (chime, spoken line and phone notification while Dale is open) are live since #177. This step lets the same 3, 2 and 1 stop alerts reach a rider whose phone is locked or whose browser is in the background. First draft: #176 comment 6936433085. Revised after Codex and CodeRabbit review on #188.

## What it never does

- It never sends the rider's location anywhere. Dale watches the locked bus, not the rider.
- It never claims the stop is near unless the server checked a fresh position of the locked bus. When it cannot check, it says so (CLAUDE.md: unknown is a valid answer).
- It never alerts from a stale, ambiguous or unmatched bus position, or while NJ Transit reports skipped stops on the trip. The rules are the same as on screen (`src/domain/rideGuide.ts`, `src/domain/stopAlert.ts`, and the skipped-stop check in `src/ui/RideMode.tsx`).
- It never switches buses. Alerts follow only the exact trip instance, service date and vehicle the rider locked (`src/domain/lock.ts`).
- It never keeps a ride after the ride ends, and never archives or logs one.

## Consent

- A new setting, separate from today's "Phone notification": "Alerts when my phone is locked", off by default. It appears in Settings and on the ride screen; both are the same setting. Turning it on explains, in English and Spanish, that while a bus is locked Dale's server keeps a short-lived ride record (trip, stops, language and a push address from the browser) and deletes it when the ride ends; then it asks for notification permission and a push subscription.
- Riders who already turned on "Phone notification" keep today's while-open alerts only. Nothing is sent to the server until they turn on the new setting themselves.
- It also needs the household code (see "Household code" below, entered once per phone).

## Flow

1. **Register a ride.** When the rider taps "I boarded" on a locked bus with the new setting on, the app first drops any earlier push subscription and creates a fresh one, so every ride has its own push address and a push still queued for an old ride can never be delivered. It then sends one `POST /v1/ride-alerts` with: the household code, the push subscription, trip instance, service date, locked vehicle, the boarding stop index, the alighting stop index, and the language. The server answers with a new ride id: 128 random bits from a cryptographic source. Before the ride counts as registered, the app writes a small record the service worker can read (IndexedDB, origin-private): ride id, push endpoint, language, and the highest stage shown so far. The ride starts as pending: the server sends nothing for it until the app, after that write succeeds, calls `POST /v1/ride-alerts/:id/activate`. The app retries activation while Dale is open; a ride not activated within 2 minutes is deleted. If the write fails, the app deletes the ride on the server at once and keeps steps A and B only. The record is replaced by the next ride and deleted when the ride ends. As built, the order is: create the ride on the server, write the service worker's record, save the ride on the phone, then activate. A ride saved on the phone can be activated, so it never exists there without its record. Before every activation try (including after Dale reopens with a lock offered back) the app checks that the record is there for this ride; if it is missing, the ride is deleted on the server instead of activated. The language is part of the ride: changing it mid-ride ends the ride and registers a new one in the new language. After every wait while a ride is starting (and before activating it), the app re-reads the saved setting and checks that the same ride is still wanted; if the setting was turned off, here or in another open Dale tab, or a different ride is now wanted, the start is abandoned: the push subscription is dropped and the record and the server ride (if already made) are deleted, and nothing is activated. The setting is read fresh from the phone's storage, and another tab's change is picked up at once (the same storage event the other settings use), so one tab never turns back on alerts another tab turned off. Opening the demo never ends a saved real ride (the demo has no real lock to compare with) unless the rider turns the setting off there.
2. **Admission checks, all in the single `BusFeed` Durable Object** (one instance, so counts live in its SQLite storage and survive restarts):
   - the household code is valid (constant-time comparison against the hash stored as a Worker secret); without it nothing is stored, so outsiders cannot use up ride slots;
   - the trip instance is active today in the schedule, and the boarding and alighting indexes are on that trip in that order;
   - the push endpoint is HTTPS on a known browser push service host (Google, Mozilla, Apple, Microsoft), so the Worker can never be pointed at an arbitrary address;
   - one active ride per push subscription (a new ride for the same subscription replaces the old one) and at most 20 in total. Because only household phones hold the code, the household cannot be crowded out by strangers.
3. **Store.** One row per active ride: id, subscription, trip, date, vehicle, boarding index, alighting index, language, last stage sent, last stage shown (confirmed by the phone), service-change flag, service-change notice state (none, pending or shown), last push time and expiry. Expiry is 30 minutes after the later of the trip's scheduled arrival at the alighting stop and NJ Transit's latest predicted arrival there, so a late bus keeps its alerts. A prediction older than 2 minutes counts as no prediction. When there is no current prediction for that stop, a bus still sending fresh positions on this trip short of the alighting stop extends the expiry to 30 minutes after its latest position. This extension applies only while the ride's own guide (the same `rideGuide` used for the countdown) places the bus short of the alighting stop; a bus reporting at or past the stop, or one the guide cannot place, never keeps the ride open. Expiry is updated each alarm, only ever moves later, and is never more than 3 hours after creation. The last stage shown starts as "riding" (rank 0) rather than empty: `stopAlertStep` treats an empty previous stage as a silent baseline, so starting at "riding" means a ride registered when the bus is already 3 stops away or closer still gets one alert for the current stage on the next check.
4. **Watch.** In its existing alarm loop, after fresh vehicle positions and trip updates arrive, the Durable Object checks each active ride with no extra NJ Transit requests:
   - If NJ Transit's trip update lists skipped stops on that trip, the ride's service-change flag is set and kept (in storage, so it survives restarts) for the rest of the ride. While it is set, no stop countdown is sent, the same as on screen. The notice state becomes pending and a push announces it. A 201 from the push service only means the push was accepted, so the notice stays pending until the phone confirms it. When the service worker gets the service-change answer from `latest`, it shows the notice, saves "notice shown" in its ride record, and then calls `POST /v1/ride-alerts/:id/notice-ack`; only that call marks the notice shown on the server. The call is safe to repeat. If its answer is lost, the next re-push finds "notice shown" in the record, replaces the notification silently and sends the acknowledgement again. While it is pending, the server pushes again every 2 minutes, including after a restart, so a failed fetch on the phone does not lose the notice. The limit is the first push plus up to 5 re-pushes, and only pushes the push service accepted count toward it.
   - Otherwise it runs `rideGuide` with the ride's boarding and alighting indexes and the latest position, then `stopAlertStep` with the last stage shown.
5. **Send, then record.** When the stage moves forward into 3 stops, 2 stops, 1 stop, last-stop-next or "ask now", the Durable Object sends a web push with a short `TTL` (60 seconds) and a `Topic` set to the ride id, so the push service drops an undelivered push after a minute and replaces an older undelivered push for the same ride with the newer one. A 201 from the push service only means the push was accepted, so the stage is recorded as sent, not shown. It counts as shown only when the phone confirms it (step 7). A push the push service did not accept is not recorded as sent at all.
   - A stage that is sent but not confirmed, including one whose push failed outright (network error, 5xx, 429), is pushed again on the next alarms (at most every 30 seconds) while it is still the current stage. A push refused for another reason (a 4xx other than 404 or 410, for example 403 after a key change) is tried again the same way, but after 3 such refusals in a row the ride ends with a tombstone (reason `push_failed`) instead of retrying until expiry. An accepted push resets that count. Once the bus moves on, only the new current stage is pushed: a stage the bus has passed is never replayed.
   - A retried or duplicated push is harmless, because the service worker removes duplicates (step 7). This is best effort: the server keeps trying while a stage is current, but a push the phone does not receive within its 60-second lifetime, or one replaced by a newer stage, can still mean a stage is missed (see "Honest limits").
6. **Payload-less push.** The push carries no data, so it needs only a VAPID-signed request (RFC 8292), not message encryption.
7. **Check on arrival.** A push carries no data and the browser does not show the service worker its `Topic`, so the `push` handler reads the ride record from step 1, confirms its endpoint matches the browser's current push subscription, and fetches `GET /v1/ride-alerts/:id/latest` (`Cache-Control: no-store`). With no matching record it shows the silent "Your Dale stop alert has ended." and asks the server to delete the ride. The server recomputes the answer at that moment rather than replaying a stored line:
   - Sound, as built: only a new, higher stage and the first service-change notice make sound. "Can't check", "ended", repeats and lower stages are always silent.
   - **active and fresh:** the ride's current stage, the line to show and the age of the bus position it came from (under 2 minutes). The handler compares the stage with the highest stage shown, stored in the ride record (not the notifications on screen, which the rider may have dismissed). Only a new, higher stage is shown with sound and saved to the record. A repeated or lower stage never sounds and never replaces the saved one: the worker re-shows the line of the highest stage already shown, silently, under the same notification tag, so a duplicate push never buzzes twice, even after a dismissal or a service-worker restart. The worker handles one push at a time (later pushes wait for the earlier one to finish). It re-reads the record, decides and saves in one IndexedDB readwrite transaction, so a ride the page ended or replaced meanwhile is never written back. It then re-checks the bus position's age, counting the time the fetch and the save took: a position more than 2 minutes old by then is shown as "can't check" and not acknowledged, whether the save worked (a saved stage is put back, with one more try if that fails, so the stage still sounds when it is next checked). Right before showing, the worker reads the record once more: if the page has ended or replaced the ride by then, it shows only the silent "Your Dale stop alert has ended." and acknowledges nothing, and if the record cannot be read it shows "can't check", puts back a stage it saved and acknowledges nothing. A ride ended in the brief moment between that last read and the notification appearing can still get this one notification and its acknowledgement, but the worker writes nothing more to the record for it. If the save of a new stage or service-change notice fails, it is shown silently and not acknowledged, so it can never sound twice. Every request the worker makes to Dale's server (`latest`, the acknowledgements and the cleanup `DELETE`) is given up after 20 seconds, so a stalled request never holds up later pushes. After showing, the worker calls the repeat-safe `POST /v1/ride-alerts/:id/ack` with the stage, and only that marks the stage shown on the server. If the fetch failed and the worker could only show "can't check", nothing is acknowledged, so the server pushes the current stage again. Because the line is the current stage, a delayed earlier push shows the newer stage instead of an out-of-date one.
   - **service change** (NJ Transit reports skipped stops on this trip): "Stops on this trip changed. Open Dale."
   - **active but not checkable** (no fresh position or ambiguous): "Dale can't check your bus right now. Open Dale." Never a claim that the stop is near.
   - **ended** (the server answers 410 with a reason: unlocked, got off, arrived, passed, expired, replaced or push_failed; `latest` itself answers 410 arrived or passed when the bus is at or past the stop): browsers require a visible notification for each push, so the handler shows a silent "Your Dale stop alert has ended."
   - **fetch failed** (offline, timeout, server error): "Dale can't check your bus right now. Open Dale." in the ride's language. Not the stop line, because nothing was checked.
8. **End.** When the rider taps "I got off", unlocks, or turns the setting off, the phone first drops its push subscription, so no further alert can reach it even if the server never hears about it, then deletes its ride record and sends `DELETE /v1/ride-alerts/:id`. If that request fails (offline), the delete is saved on the phone and retried whenever Dale opens, the network returns, and every minute while Dale is open; meanwhile the setting shows as off with "Removing your ride from Dale's server...". The row is deleted on that `DELETE`, at expiry, when the stage reaches arrived or passed, or when the push service answers 404 or 410 (which it does for a dropped subscription, so an unacknowledged delete still ends at the next push attempt). A short tombstone (id and reason, no subscription) is kept until expiry so `latest` can answer "ended" in step 7. Only the Dale tab holding the lock ends the ride for "I got off" or unlock; another open Dale tab that learns of the ride ends it only once the live lock saved on the phone is gone or is a different lock, or the setting is turned off.

## API routes (as built)

All answers are JSON with `cache-control: no-store`. Writes need Dale's own page as the `Origin`. A ride id is 22 base64url characters.

- `GET /v1/ride-alerts/config`: whether alerts are available, and the VAPID public key the app subscribes with.
- `POST /v1/ride-alerts`: register a ride (step 1). Starts pending.
- `POST /v1/ride-alerts/:id/activate`: start watching a pending ride.
- `GET /v1/ride-alerts/:id/latest`: the answer for the service worker (step 7), recomputed now.
- `POST /v1/ride-alerts/:id/ack`: the phone showed this stage.
- `POST /v1/ride-alerts/:id/notice-ack`: the phone showed the service-change notice.
- `DELETE /v1/ride-alerts/:id?reason=got_off|unlocked`: end the ride (step 8).

## Owner step

- VAPID needs a P-256 key pair. Jeff makes it, with the household code and its hash, on the key page `public/owner-keys.html` (published as `owner-keys.html` beside the app). The page runs only in his browser; its Content-Security-Policy blocks every network request, and nothing is saved. The builder never sees, commits or prints the private key or the code.
- Order: the weekly rollover first, then the secrets. Adding a secret in the Cloudflare dashboard ends with Deploy, which makes a new Worker version, so the next rollover's `expected_worker_version` comes from a fresh `qualify-enabled` run. The deploy script accepts these two names only as secrets, and deploys keep existing secrets.
- Jeff stores the private key as a Cloudflare secret, `VAPID_PRIVATE_KEY`: the private key as a P-256 JWK (JSON with `kty`, `crv`, `x`, `y` and `d`), with step-by-step help. The public key is not secret; the Worker derives it from that key and serves it at `GET /v1/ride-alerts/config`, so nothing key-related is in the repository.
- The household code's hash is a second Worker secret, `HOUSEHOLD_CODE_HASH`: the lowercase hex SHA-256 of the household code after normalizing it (trimmed, upper case, spaces and hyphens removed). The code itself is described under "Household code" below.
- If either secret is missing or malformed, every ride-alert route answers "not available" and the app keeps steps A and B only.

## Privacy and limits

- A push endpoint is a capability URL. It is stored only for the life of one ride, is never logged, archived or shown in health output, and is deleted when the ride ends.
- If a delete cannot reach the server, the ride row (trip, stop indexes and a push address that no longer works) can stay until the next push attempt or its expiry, at most 3 hours after creation. The setting's explanation says so.
- The boarding and alighting stop indexes are stored for the life of the ride only, because the server needs them to count stops; they are never archived. This is why the setting has its own consent.
- Writes per ride, as built. Each check writes a ride at most once. Its lock and position history are written only when its sent stage, service-change notice, lock status, service-change flag or expiry changes (expiry counts once it has moved 2 minutes or more, or when the stored expiry is within 2 minutes of running out), and otherwise at most once every 2 minutes. A sent stage is written together with its push; a repeat push of the same stage is not written. So a ride with a steady bus writes about 30 rows an hour (tested over an hour of fresh positions), plus at most about 20 over its life: create, activate, up to 5 sent stages, up to 6 notice pushes, up to 3 refused pushes, the end and the tombstone's removal. While any ride is active and collection is on, the Durable Object also stores the history schedule once per history run (at most 2,880 rows a day).
- Between writes, the Durable Object keeps each active ride's lock and position history in memory and uses it for both the alarm check and `latest`, so every position it accepted counts, exactly as on the phone; the stored row is only the fallback after a restart, and the memory copy is dropped when the ride ends, including when the expiry cleanup ends the last ride.
- What a restart can lose because of this: at most 2 minutes of the bus's position history (the guide then rebuilds it from the next positions). Never a stage already sent, a notice state or a refused-push count, because those are written with the push itself.
- Worst case for the budget: 20 rides all day, each lasting its full 3 hours, with buses reporting normally, is about 20 x 24 x 30 = 14,400 rows, plus about 3,200 for the rides' lives (8 rides a day in each of 20 places, about 20 rows each), plus 2,880 for the schedule: about 20,500 rows a day. With history collection's own cap of 75,000 a day (`docs/HISTORY_COLLECTION.md`), that stays under the Free plan's 100,000 rows written a day. A bus feed that keeps dropping out for over 2 minutes and coming back adds up to 2 rows per dropout per ride.
- Rides never change when or how often history collection runs: collection, archive flush and hot-row prune keep their own schedule (including the hourly retry while collection waits at its storage limit), a ride's poll never starts a history attempt, and a ride check due within one poll before a history run waits for that run. The next history run's time is fixed before any ride's push is sent, so slow pushes never make it later, and once it is due the alarm starts no further ride checks (the rides it skipped are checked first at the next alarm; each ride's own pushes stay in order).
- No new vendor and nothing paid: browser push services are free and are reached only through the subscription the rider's own browser created.

## Honest limits, shown in the app

- Alerts depend on live bus GPS reaching the Worker. When the bus stops reporting, no countdown is sent, the same as on screen; the app says so beside the setting.
- A push the phone does not receive within 60 seconds is dropped by design, so a rider with no signal may miss a stage rather than get it late.
- iPhone needs Dale added to the Home Screen (iOS 16.4 or later). The push service, not Dale, decides how fast a notification arrives.
- Like all of Dale's live data, alerts share the Worker's free daily request allowance (see `docs/RIDER_GPS.md`, "Remaining risk Jeff should know about").

## Tests before release (planned; unit and browser tests now written in #192)

- Unit: the server's stage decision matches the app's for the same positions, including stale, ambiguous, off-route and skipped-stop cases, and the service-change flag surviving a restart; a ride registered inside 3 stops alerts once; send-then-record with a failed push, a lost answer (duplicate) and a restart; the household code, endpoint host allow list and caps; expiry, tombstones and 404/410 deletion.
- Browser: two pushes whose `latest` answers arrive out of order never let the older stage replace or sound over the newer one; a slow answer whose position is over 2 minutes old by display time shows "can't check" and is not acknowledged.
- Unit: an outdated prediction is ignored for expiry.
- Unit: a sent but unacknowledged stage is pushed again while current and never after the bus moves on; a late bus with no prediction for the alighting stop keeps its ride while it reports fresh positions, within the 3-hour cap.
- Unit: a ride sends nothing until it is activated, and a pending ride is deleted after 2 minutes; a service-change notice stays pending after a 201 until `latest` returns it, is re-pushed after a failed fetch and after a restart, and stops after the phone acknowledges it or after 5 tries; a lost acknowledgement is resent without a second sound; a late bus keeps its ride until 30 minutes after its predicted arrival, within the 3-hour cap.
- Browser: the service worker's cases in step 7 (fresh, service change, not checkable, ended, fetch failed, no matching record); a duplicate after the rider dismissed the first notification stays silent; a push for a replaced ride is never shown; an offline opt-out is retried later. In English and Spanish.
- Household on-road test on an Android phone and an iPhone before the feature is described as working.

## Household code

Moved here from `docs/RIDER_GPS.md` when rider-shared positions became open to any Dale rider (owner choice, Nov 17); locked-phone alerts are now its only user.

- Made on the owner key page (`public/owner-keys.html`) with the browser's cryptographic random source: 16 characters from a 32-character alphabet without I, O, 0 and 1 (80 bits). Only its hash is stored, as the Worker secret `HOUSEHOLD_CODE_HASH` the owner sets.
- Rotating it is one owner step: make a new set on the key page and store the new hash. Every phone then asks for the new code.
- Every request's code is checked with a constant-time hash comparison, and a correct code is always accepted while the Worker is answering, so nobody else's wrong guesses on a shared address can lock out the household. Guessing an 80-bit code within the Free plan's 100,000 requests a day is not practical. After 5 wrong codes in 10 minutes from one network address (kept only in memory for that window), that address's later wrong codes get "try again later" for 1 hour (`WrongCodes` in `worker/ride-alerts.ts`, at most 1,000 addresses tracked). The earlier design's health warning for many wrong codes across all addresses is not built.
- It is never logged, archived or shown in health output.
