## Architecture and evidence

- Reuse `dale-live`, SQLite `BusFeed/corridor-v1`, canonical G2 normalization, token reuse and the same globally paced30-second refresh. Demand and native alarm work serialize/coalesce. No second poller, scheduler, vendor, service, package or rider tracking. D75 adds optional statewide rail GTFS-RT originals on the same refresh owner, at most once per 30 seconds; it never background-polls RailData. D77 authorizes further statewide bus and rail expansion through the linked plan, within the same owner and shared limits.
- One private SQL bundle per completed attempt holds normalized GPS observations, source-generation/observation/receipt clocks, static version, route/direction/service-date identity and quality diagnostics. Separate cancellation/skip context retains its own source clock; predicted arrival values are not treated as actual arrivals. A stopped-at sample does not identify the exact instant of arrival.
- The current compact corridor per-poll vehicle/trip/source-timestamp census retains unchanged and rejected presence. D77's linked plan expands the archive input beyond the corridor; D83 now limits raw bus entities to routes serving the four counties while keeping this corridor interpretation for the app. Deduplicated GPS counts remain separate. An absent bus is not assumed unchanged, cancelled or arrived. Unknown census/oversized omissions stay explicit.
- Before recording under each static version, retain the complete canonical trip/pattern/stop/calendar/timezone context in private atomic chunks. Old versions are not removed. This preserves retrospective arrival analysis after schedule rollover. Unknown/expired matches remain unknown; refresh finite static coverage through the existing manual reviewed-main workflow.
- Context keys include a SHA256 of the complete canonical build, so converter/context changes under an unchanged upstream feed version cannot silently reuse different historical schedules. Old context may leave hot SQLite only after its complete original archive and manifest are verified; its durable archive remains.
- Bundle and dedupe checkpoint commit atomically; a failed write rolls back both. Watermark expiry only removes short-lived dedupe metadata, not historical bundles. Quality-only rows retain missing/stale/invalid/empty polls and omissions. D75, narrowed by D83, separately preserves regional bus and whole rail raw feeds as described below; normalized corridor bundles keep their existing format. No rider location, credential or token is archived. D77 authorizes further private expansion through the linked plan.
- `/v1/collection` exposes read-only health/counts/clocks/reasons/size/alarm state, never bus identities, coordinates, datasets or private watermarks. Reading it does not poll upstream. There is no public raw-history/export/start endpoint. The separate owner-secret observation reader, off unless its secret is set, is documented in [OWNER_HISTORY.md](OWNER_HISTORY.md) (#250, owner clarification Nov 21).

## Regional bus raw feeds and whole rail originals (D75/D83; deployment not checked)

D75 is the owner decision and reason for expanding the former corridor-only archive restriction, including the corridor-only sentence in `CLAUDE.md`. Jeff's November 22 follow-up selects rail GTFS-RT, not RailData background polling, because NJ Transit's RailData guide limits that API to specific user requests. It does not change the normalized corridor archive, authorize publication, or deploy this build.

- Bus responses are decoded and re-encoded with only vehicle/trip-update entities whose exact `trip.routeId` serves a stop inside Bergen, Essex, Hudson or Passaic, using the same static GTFS download and the supplied US Census county polygons (holes excluded). Routes qualify through any trip and stop; invalid/missing coordinates count as outside. The agency header stays unchanged. Entities without a route ID and alerts are dropped. Rail protobuf responses stay whole, as received, without re-encoding. Equal saved bodies on different polls get separate objects; receipt replay recovers the same object without counting it twice. This changes only raw saving, never live normalization or corridor history.
- Preparation writes separate `worker/generated/region-routes.json` with version, static feed version, county names and sorted route IDs. A build error or zero qualifying routes writes `null` and logs one aggregate line without stopping preparation. A null, missing, malformed, empty or mismatched asset saves no bus raw responses and reports raw status `region-unavailable`; rail and corridor history continue. A bus protobuf decode failure saves no raw object and increments that feed's `invalid-response` failure count.
- Bus keys: `raw/v1/<UTC receipt date>/<getVehiclePositions|getTripUpdates>/<epochMs>-<saved SHA256>.pb.gz`. Rail keys: `raw/v1/<UTC receipt date>/rail-<getVehiclePositions|getTripUpdates>/<epochMs>-<saved SHA256>.pb.gz`. RailData keys (D84): `raw/v1/<UTC receipt date>/raildata-poll/<epochMs>-<saved SHA256>.json.gz`, one JSON bundle per poll holding each answer's exact text (base64 if it is not UTF-8) or its fixed failure code, and the daily `raildata-getStationList` and `raildata-getStationSchedule` answers whole. BUSDV2 keys (D84): `raw/v1/<UTC receipt date>/busdv-poll/<epochMs>-<saved SHA256>.json.gz`, one bundle per poll the same way, and the daily `busdv-getLocations` and `busdv-getBusRoutes` answers whole as `<epochMs>-<mode>-<saved SHA256>.json.gz`, with the mode (BUS, NLR, HBLR, RL) also in the manifest's `label`. UTC folders partition receipts, never Eastern service dates. Overnight trips and schedule contexts retain their original evidence, and UTC hours distinguish the repeated Eastern hour at daylight saving changes.
- Each saved response has an adjacent `.manifest.json`: feed, receipt time, saved/gzip sizes and SHA256 hashes, upstream protobuf header timestamp in seconds (null when absent/unreadable), count and identical-to-previous flag. Filtered buses add `filtered: { v: 1, counties, sourceSHA256, sourceBytes, entities, kept, noRoute }`: original-response hash/size, original entity count, kept count and count without a route ID. `sha256` remains the hash of saved filtered bytes. The discarded original body is never archived. No request fields, HTTP headers, credentials or tokens are saved. Secret checks still inspect original response bytes, including discarded entities; echoes reject the response rather than redact evidence.
- Per-feed hourly verified count, saved/gzip byte totals and identical count live in the existing private relay checkpoint. Fixed failure codes have separate per-feed `events` counters. A `response-too-large` event increments the missing counter; no partial body is saved or counted as an original. Closed UTC hours are written immutably at `raw/v1/<date>/ledgers/<HH>.json` after interrupted originals for that hour reconcile. Public health exposes totals and fixed reasons only, never keys, hashes, identities or bodies. Each new original is taken only if 4096 bytes stay reserved for every hourly ledger still open, and a finished hour closes on its own reservation, so reaching the raw byte stop never leaves an hour's ledger unwritten (Neon, #278). If R2 operation capacity is exhausted, these counters remain in the checkpoint and ledger upload waits until the rolling window frees operations.
- Raw saving accepts at most 32 MiB (33,554,432 bytes) per complete response. This is Dale's own memory guard, raised from 8 MiB for raw saving at Jeff's November 22 request, not an NJ Transit response-size limit. Streaming overflow is cancelled and counted. Disabled raw saving keeps the existing 8 MiB bus guard. Real response sizes and Worker memory/CPU headroom are **not checked**.
- The four feeds share one extra checkpoint per normal poll. The normal relay completion saves acknowledgments in its existing final write. Recovery consumes another reserved checkpoint. Intents hold small manifests rather than full bodies. After a crash, an existing original is verified and its manifest repaired before counting it. Bytes that never reached R2 cannot be recovered from metadata and are counted missing. Transient recovery failures retain intents. Eight unresolved intents per feed bound checkpoint growth; omissions are counted while other feeds continue.
- Raw storage buys conservative byte/Class A/Class B/checkpoint-write reservations from the existing shared archive ledger. It stops before the shared 500,000,000,000-byte cap (D86), rolling operation caps or spare SQL write budget; failed/ambiguous grants are not refunded. Unused capacity is deliberately over-reserved. Existing corridor archives, originals, manifests, verified hot-prune conditions and the private bucket stay intact. No R2 overwrite or deletion is added.
