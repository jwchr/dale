## Calls and field meanings
- Use POST BUSDV2 `getBusDV`, with server-held `token`, `stop=PABT`, an explicitly verified outbound `direction`, and one verified corridor `route` per request. Never use the sample's blank route to fetch a systemwide board.
- The doc says: "Provides a list of trips matching the given criteria that will be active 1 hour."
- Read `DVTrip.public_route`, `sched_dep_time`, `timing_point_id`, `internal_trip_number`, and `lanegate`. The sample requests `stop=PABT` but returns `timing_point_id: "NWYKPABT"`, and `DVTrip` has no direction field. Match the terminal through a verified `timing_point_id` allowlist (complete PABT values: **not checked**) and get direction only from the verified request parameter plus outbound-only canonical candidates. Ignore relative `departuretime` for identity. Discard vehicle fields before public serialization.
- The example contains `"lanegate": "311"`. A `"lanegate": "222-3"` example is on page 10 under `getRouteTrips`, not page 13's `getBusDV` example.
- Related POST `getTripStops` takes `token`, `timing_point_id`, `sched_dep_time`, `internal_trip_number` from DV. The doc says: "Provides the list of stops that the requested trip will make."
- Its PABT example shows `"SchedLaneGate": "311"` and `"ManLaneGate": ""`. Definitions of scheduled versus manual, override precedence, and their relationship to `lanegate`: **not checked**, because this doc does not say. Do not assume ManLaneGate overrides SchedLaneGate.
- Use `getBusDV.lanegate` alone in slice 1; no per-trip `getTripStops` fan-out. Door syntax is Dale's existing parser interpretation, not a definition in these pages; confirm against an approved private board sample before claiming real gate/door acceptance.

## Exact trip-instance match
- Build candidates from the active canonical corridor schedule, PABT boarding stops, active service dates, outbound direction and boarding eligibility. Include prior service date's departures after midnight, and between 23:00 and 23:59 Eastern also include the next service date's 00:00 to 00:59 departures, so the one-hour lookahead covers both encodings.
- Parse `sched_dep_time` as a complete America/New_York local date/time with explicit rules, never browser Date guessing. The doc does not specify timezone or DST encoding: **not checked**; verify before live matching.
- Require route/variant agreement through a verified API-to-canonical mapping, identical scheduled PABT departure instant (zero tolerance), and the correct canonical service date. The wall calendar date can differ for GTFS times over 24:00.
- Match exactly one canonical `tripId@serviceDate` plus its PABT boarding index; one trip can serve two PABT stops (26229 and 31860 in the `getTripStops` sample). Never match route alone, nearest time, predicted time, or assume `internal_trip_number` equals GTFS trip ID. Estimated schedule times cannot establish identity.
- Drop and count unmatched, ambiguous, conflicting duplicate, wrong-terminal/direction and invalid-date rows. Distinguish reasons using totals only. Reject DST gaps/repeated times without an independently confirmed disambiguator.
- Pin each snapshot to `feedVersion`; clear postings on schedule rollover. A slow response from the previous feed or an older poll cannot replace current evidence.

## Polling and daily budget
- Reuse the existing private corridor Durable Object and alarm owner, coalescing all readers. Proposed gate cadence: once per 60 seconds per eligible route, only when an active canonical PABT departure is within the next 60 minutes. A 90-minute trigger would not extend the doc's one-hour coverage.
- The prepared corridor is 163, 164, 165, 165T (`scripts/prepare-live-worker.mjs:65`). Verify API route/variant mapping; deduplicate variants sharing one API route. Bound at four route requests per minute; stop gate polling when no route is eligible. No rider-driven cadence or new collector.
- Conservative 24-hour all-active bound: 4 x 1,440 = 5,760 gate calls. Existing G2: 2 x 2,880 = 5,760 feed calls. Combined 11,520 before authentication, retries and schedule downloads, below 40,000 even if treated as one budget.
- A 25-hour Eastern day yields 6,000 + 6,000 = 12,000. The brief 5-second cadence test (`worker/history-journal.ts:143`) must be counted by actual attempts, not assumed to run all day. Never make DV follow that faster cadence.
- `worker/service.ts:243` persists pace before I/O and reuses a token for 20 hours with a one-hour auth cooldown. `worker/history-journal.ts:14` reserves against 75,000 storage writes/day, not NJT requests; gate writes must fit its existing Free limits too.
- Add durable atomic attempt reservations per API before network I/O, including failures, authentication, retries and restart recovery. Fail closed before 40,000/day; reserve gate traffic at at most 6,500/day and maintain a conservative combined 40,000 ceiling until API quota boundaries are verified.
- Count all other callers, including preparation/download jobs, against their API allowance; unknown outside usage blocks a claim of guaranteed headroom. Use a rolling 24-hour ceiling plus Eastern-day accounting to cover unknown quota reset timing and DST.
- `agreement.txt:14` says 100,000/day, but Jeff's instruction and project rules impose the stricter 40,000/day per API here. Do not raise it. Include failed/retried requests in all arithmetic; no immediate token retry loop or paid overflow.

## Worker and UI contract
- Proposed `GET /v1/gates`: one bounded cached corridor-wide response, no query parameters, rider IDs, locations, locks or favorites. Viewers read the same snapshot; no direct browser requests to NJ Transit.
- Envelope: `{ schemaVersion, feedVersion, generatedAt, routes, postings }`, where `routes` holds per-route `{ route, state, lastSuccessAt, lastAttemptAt }`; states include ready, empty, stale, unavailable and quota-paused. A response failure or empty board on one route changes only that route's state and postings.
- Each posting: `{ tripInstanceId, boardingIndex, gate, door?, source: 'njt-departurevision', receivedAt, observedAt, ageMs, expiresAt }`. Recompute `ageMs` on every Worker read, adding any cache `Age`, and in the UI anchor age to the served `ageMs` plus the whole request duration (monotonic `performance.now()` from request start, since transit after serialization is not in `ageMs` or cache `Age`) plus time since the response arrived, never to device `Date.now()` minus server timestamps, so a skewed phone clock cannot extend or cut freshness. On resume from background, refetch before showing a posted gate; if the elapsed time cannot be trusted, treat the posting as expired.
- The shown DV rows have no gate-update timestamp. Use receipt time as observedAt with an explicit receipt-time label; source assignment age is **not checked**, not proven fresh by a repeated value. Keep any future verified agency clock separate.
- Proposed freshness cutoff: 120 seconds since receipt, exclusive. At 120 seconds or later remove from eligible postings even offline/backgrounded; over 60 seconds show "may not be real time" per agreement line 10. Never let new response generation reset gate age.
- Extend `GatePosting` with `boardingIndex` and expiry, make `gateFor` match trip instance and boarding index and drop expired postings, and have `departureGate` (`src/ui/App.tsx:1376`) pass the departure's stop index. Then pass validated eligible postings to the `posted` path on home, Gates and trip detail, displaying source, receipt age and door in English and Spanish. Without eligible postings use published/unknown; no demo usual gates in real mode. Preserve the printed source/effective date and official-board guidance.
- Gate validation accepts bounded documented numeric forms only after verification; empty, null, dots such as `..`, malformed or oversized text is no gate. Change `parseLaneGate` (or add a strict live validator in front of it) so non-matching text returns null instead of `{ gate: text }`. The code calls `..` inbound; that meaning is **not checked** in these API pages.

## Failures, history and later notices
- P1 wrong trip/gate: reject ambiguous mapping and dates; test same-route simultaneous departures, midnight and DST. Do not render a guessed gate.
- P1 stale or changed gate: expire on the client clock too; an HTTP 200 board with an empty `DVTrip` list clears that route's assignments only, and an error never renews age. Replace a changed gate/door only with newer matched evidence; a missing row means not reporting, never cancelled.
- P1 privacy/security: allowlist verified production hosts, redact tokens/raw bodies/vehicle IDs, cap bytes/rows and timeouts, refuse redirects. Diagnostics contain operation, safe cause, attempt/last-success times, source version, age and aggregate drop/quota counts only.
- P2 denied/expired token, 429, unavailable service or a malformed or empty response body (not a valid empty `DVTrip` list), per route: bounded backoff and explicit state, retain old evidence only with its original age, then fall back. Keep bus G2 failures and BUSDV2 failures separate so one does not disable the other.
- P2 overlapping polls, crash or quota/storage exhaustion: reserve durably, serialize updates, discard older completions, pause gate work without breaking existing bus collection. Verify restart and boundary behavior.
- Recommendation: keep matched gate postings and their source/context privately for future usual gates, under `docs/HISTORY_COLLECTION.md`, as a separately reviewed history slice. Do not enable new archival writes in slice 1.
- That slice must preserve changes, absences and poll quality with canonical schedule context, deterministic poll IDs, atomic commits and immutable archive/readback before hot cleanup. Retries must neither lose nor double count evidence. Public history output remains totals only; no raw endpoint or recordings in git/logs.
- Later GATE-03 slice: compare fresh postings for the same locked trip/date/boarding stop, notify a gate or door change once using a durable event key, and never switch buses. Reuse existing ride/Web Push machinery; permission denial, expired locks, duplicate/reordered updates and English/Spanish notices need tests. Actual locked-phone delivery remains a device acceptance check.
- Usual gates remain a separately labeled historical estimate with sample count, source window and age, never posted/live. Sampling comparable service days and gate changes needs evidence before choosing a rule.
