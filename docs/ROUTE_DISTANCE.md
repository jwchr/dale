# Observed bus route distance (#113)

This feature reports approximate remaining **route** distance from an actual NJ Transit bus GPS observation. Before boarding, the target is the selected boarding stop. On board, the target is the rider's selected destination. It does not use rider GPS, move with a timetable, predict arrival, confirm a stop, choose a different bus or change either arrival clock.

## Source and identity

The existing static preparation downloads one G2 ZIP. `buildRouteGeometry` derives a separate version-bound delivery asset from that same ZIP, joining each exact `trip_id` to its own `shape_id` and ordered stop calls. Trips sharing a stop pattern can have different shapes. Source `shape_dist_traveled` is only an interpolation parameter; its units are not assumed to be meters. Original road-path lengths are calculated in meters and retained through bounded simplification (4m screening tolerance). Preparation requires stop mappings within100m of published stop coordinates. Delivery also validates the actual coordinate at each mapped meter value against its canonical stop, allowing105m for the source tolerance plus4m simplification/rounding. Monotonic but spatially wrong offsets (including a distant destination mapped to0) are rejected. Valid repeated stops/loops remain eligible with explicit stop anchors resolving shared locations. Missing, conflicting or invalid source mappings are omitted.

`/v1/geometry?feedVersion=…` is a static read-only response. It does not invoke the feed actor, authenticate or fetch NJ Transit. It rejects other feed versions. Invalid optional geometry disables that response; it cannot throw during router initialization and break the recorder or schedule service. The browser shares one bounded optional request per endpoint/version per opening; failures remain unavailable for that opening. Geometry is capped at4MB decoded,256shapes,2000trips and50000points. The source ZIP full SHA-256 must match the canonical feed-version prefix. An older archive cannot fill missing geometry in a different deployed feed.

The existing coalesced departures snapshot can include one exact-trip GPS observation. Original vehicle/observation timestamps are preserved. Ambiguous vehicles, contradictory latest fixes and unresolved dates supply no coordinates. This adds no upstream request or browser polling interval. Waiting/onboard use the existing accepted official lock history and exact vehicle identity. The locked snapshot groups by exact trip/vehicle and rejects contradictory newest equal-time coordinates/statuses instead of arbitrarily choosing one. Valid distinct vehicles and reassignment evidence remain visible; a conflict invalidates current GPS qualification. Identical duplicates or a strictly newer resolved sample remain valid. Raw recorder evidence is unchanged. Home separately flags ambiguous GPS, clears cached distance immediately and retains independent valid arrival predictions; a newly missing GPS report marks any retained distance as Last GPS.

## Geometry failure diagnostic

When preparation fails at `geometry-validation`, it prints one extra line before the existing failure line: `Geometry diagnostic (aggregate counts only): {"v":1,"reason":…,"counts":{…}}`. The reason is one of `source-mismatch`, `shape-limit`, `trip-limit`, `point-limit`, `byte-limit`, `no-matched-trips` or `unexpected-exception` (any other builder exception, with its message dropped because it can name columns). `counts` uses a fixed key list: header presence flags for the measure and shape columns, how many trips/shapes were requested, found and valid, one counter per rejection reason (for example `tripMissingMeasure`, `tripMeasureOutOfRange`, `tripStopDistance`) and the matched totals. Each value must be a nonnegative integer up to 1,000,000, or the whole `counts` becomes `null`. No trip, shape or stop IDs, coordinates, feed rows, ZIP bytes or error messages are printed. The delivered geometry is unchanged: the builder computes the same output and only records why each shape or trip was or was not included. This is source observability only; it authorizes no new run, retry, preparation or deployment.

## Rider behavior

A compact label shows `≈ 2.9 mi away · NJT GPS 15s` (English/Spanish). On board it names the remaining distance to the destination. Geometry, trip/date, stop order and vehicle must agree. Projection farther than100m off the route, ambiguous nearby route legs separated by more than100m of route progress, or a position beyond the target produce no distance. An explicit validated `stopped_at` observation can resolve a nearby repeated route leg; proximity alone cannot.

A missing feed keeps only the last qualified observed distance, marked Last GPS and continuing to age. Beyond120seconds it is stale even if later receipts repeat the same source timestamp. New off-route evidence does not make an old distance look current. Pending vehicle replacement, cancellation, closed rides and known lock stop changes suppress the display. No report yields a schedule-derived or straight-line distance.

## Deterministic response-order regression

The recovery/off-route browser case deliberately holds the resumed response in flight. The original observed-at attribute already existed before recovery, so it was not an acceptance barrier: two immediate visibility wakes could be coalesced by the legitimate running-request guard. The corrected case proves that the recovered duplicate packet finished and rendered available without changing its source timestamp, then verifies the new off-route response coordinates/timestamp, keeps the exact trip row visible and requires no distance. No polling interval, timeout or accessibility assertion is relaxed. The structural race was identified in source; synthetic held-response execution is not a replay of the original failed CI trace.
