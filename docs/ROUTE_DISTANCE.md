# Observed bus route distance (#113)

This feature reports approximate remaining **route** distance from an actual NJ Transit bus GPS observation. Before boarding, the target is the selected boarding stop. On board, the target is the rider's selected destination. It does not use rider GPS, move with a timetable, predict arrival, confirm a stop, choose a different bus or change either arrival clock.

## Source and identity

The existing static preparation downloads one G2 ZIP. `buildRouteGeometry` derives a separate version-bound delivery asset from that same ZIP, joining each exact `trip_id` to its own `shape_id` and ordered stop calls. Trips sharing a stop pattern can have different shapes. Source `shape_dist_traveled` is only an interpolation parameter; its units are not assumed to be meters. Original road-path lengths are calculated in meters and retained through bounded simplification (4m screening tolerance). Preparation requires stop mappings within100m of published stop coordinates. Delivery also validates the actual coordinate at each mapped meter value against its canonical stop, allowing105m for the source tolerance plus4m simplification/rounding. Monotonic but spatially wrong offsets (including a distant destination mapped to0) are rejected. Valid repeated stops/loops remain eligible with explicit stop anchors resolving shared locations. Missing, conflicting or invalid source mappings are omitted.

`/v1/geometry?feedVersion=…` is a static read-only response. It does not invoke the feed actor, authenticate or fetch NJ Transit. It rejects other feed versions. Invalid optional geometry disables that response; it cannot throw during router initialization and break the recorder or schedule service. The browser shares one bounded optional request per endpoint/version per opening; failures remain unavailable for that opening. Geometry is capped at4MB decoded,256shapes,2000trips and50000points. The source ZIP full SHA-256 must match the canonical feed-version prefix. An older archive cannot fill missing geometry in a different deployed feed.

The existing coalesced departures snapshot can include one exact-trip GPS observation. Original vehicle/observation timestamps are preserved. Ambiguous vehicles, contradictory latest fixes and unresolved dates supply no coordinates. This adds no upstream request or browser polling interval. Waiting/onboard use the existing accepted official lock history and exact vehicle identity. The locked snapshot groups by exact trip/vehicle and rejects contradictory newest equal-time coordinates/statuses instead of arbitrarily choosing one. Valid distinct vehicles and reassignment evidence remain visible; a conflict invalidates current GPS qualification. Identical duplicates or a strictly newer resolved sample remain valid. Raw recorder evidence is unchanged. Home separately flags ambiguous GPS, clears cached distance immediately and retains independent valid arrival predictions; a newly missing GPS report marks any retained distance as Last GPS.

## Rider behavior

A compact label shows `≈ 2.9 mi away · NJT GPS 15s` (English/Spanish). On board it names the remaining distance to the destination. Geometry, trip/date, stop order and vehicle must agree. Projection farther than100m off the route, ambiguous nearby route legs separated by more than100m of route progress, or a position beyond the target produce no distance. An explicit validated `stopped_at` observation can resolve a nearby repeated route leg; proximity alone cannot.

A missing feed keeps only the last qualified observed distance, marked Last GPS and continuing to age. Beyond120seconds it is stale even if later receipts repeat the same source timestamp. New off-route evidence does not make an old distance look current. Pending vehicle replacement, cancellation, closed rides and known lock stop changes suppress the display. No report yields a schedule-derived or straight-line distance.

## Recorder and release boundaries

Geometry is not a Dataset field and is never passed to `createFeedClass`, `HistoryJournal` or the archive. Canonical JSON bytes, `historyContextKey`, context size and the journal's reservations/write budgets are unchanged for the same canonical input. Tests compare original JSON/hash and ensure static delivery never touches the actor. The collection interval and all collector/archive limits remain unchanged.

Source tests use synthetic inputs. A private older local archive experiment may establish implementation size/coverage, never current-feed acceptance. The builder must not run real preparation, authentication/downloads, a Worker update, collector stop/restart or a collection-coupled workflow mode. Exact-head CI, independent HIGH full-diff review and the separate operator's data/deployment/public gates remain required. Publishing the frontend alone does not establish availability: the operator must qualify matched current geometry and GPS on the actual deployed backend while preserving the running recorder.

## Existing enabled-collector update mode

The existing manual main-only workflow adds `preserve-enabled`; it is not an activation, stop, retry or migration. The operator must separately authorize a real run and supply both the current active Worker version UUID and exact canonical `feedVersion:SHA256` context. Default disabled, initial enable, strict inspection and restore-disabled behavior remain distinct. Never choose restore-disabled for an enabled recorder.

Before any NJT authentication, preservation preparation brackets the active Worker identity, requires the existing enabled FEED namespace/private dale-history bucket/secret bindings, and validates bounded read-only schedule/collection receipts against those pins. It preserves the exact compact canonical JSON bytes (builtAt/city labels included). The single existing ZIP download must match that canonical feedVersion; changed ZIP/context, disabled/unhealthy collector, unknown counters, active cadence experiment, missing geometry or inadequate existing Free-budget headroom fail before writing/upload. City decoration is not refreshed. A changed provider ZIP needs a separately reviewed migration; this mode cannot invent or graft old geometry.

Deployment rechecks the private preparation receipt against the still-active version, exact canonical bytes and current aggregate checkpoint. Existing strict executable/data module, runtime and resource/binding proofs remain. HISTORY_COLLECTION stays enabled. Preservation inherits existing secret bindings and does not rewrite credentials with a secrets file, retaining provider rollback compatibility where supported. After upload, read-only collection checks require unchanged canonical context/limits, future native alarm, nonregressing cumulative observations/batches/attempt/archive reservations and new native completion/archive progress within the existing bounded readiness window. This mode does not call status/live demand paths or NJT; current geometry/GPS/public acceptance remains separate. Hot bytes can shrink only through the unchanged verified archive-before-prune implementation; aggregate counters alone do not prove every archived object. An interrupted in-flight attempt is reported honestly, never called zero-gap continuity.

Failure holds the release and leaves collection/evidence intact. There is no automatic retry, disable or rollback. The preparation receipt also emits a compact non-secret rollback reference containing only the previously observed version, context, etag and full content/runtime/binding hashes plus a reference digest. It includes no credentials, namespace descriptors, code or transit records. Its full manifest/context observation is captured while that version is actually active and bracketed; a UUID/etag alone cannot replace that source proof. The reference is evidence, never review or permission.

## Explicit guarded rollback in the same workflow

`rollback-enabled` is a separate manual main-only choice in the existing workflow, not a failure handler. It requires the operator's pinned CURRENT version/context and an independently qualified prior reference/digest. Before authorization, the non-author operator must establish that target code is the reviewed code represented by the prior full-content observation and remains compatible with the present journal/storage. Source tests cannot establish that actual account access, provider eligibility or target storage compatibility.

The script verifies current enabled collection/budgets/context, exact target availability in the provider's bounded deployable list, immutable version/etag and matching runtime/migration/resource/credential descriptors. Target and current canonical context and resources must match. It rechecks the active identity and fresh cumulative evidence before issuing exactly one explicit version deployment to100% traffic. This uses the same deployment operation as pinned Wrangler4.158.0 rollback, without interactive defaults, a `force` parameter, credential rewriting, settings/resource mutation or retries. Provider refusal for changed secrets, missing resources, incompatible lifecycle changes or unavailable targets is terminal; never auto-confirm or retry with force.

Afterward, only an explicitly pinned older active version may bypass the ordinary active-equals-latest requirement. Full module-manifest/runtime/binding hashes must still match the original observed reference; script-scoped content from a different/latest version is rejected, never relabeled as historical target bytes. Exact canonical bytes, enabled/native alarm, cumulative evidence/budgets and new native completion/archive progress remain required. Deferred code update uses the provider's300second maximum and a bounded360second read-only progress window. Isolate interruption remains possible and is recorded honestly; persistent DO/R2 state is not rolled back, reset or deleted. Failed proof holds release with no automatic stop, second rollback or fallback. Actual access, deployed behavior and recorder/public acceptance require separate operator evidence.

Provider references: [Workers rollbacks and resource limitations](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/), [deployment API and force semantics](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/deployments/methods/create/). ## Deterministic response-order regression

The recovery/off-route browser case deliberately holds the resumed response in flight. The original observed-at attribute already existed before recovery, so it was not an acceptance barrier: two immediate visibility wakes could be coalesced by the legitimate running-request guard. The corrected case proves that the recovered duplicate packet finished and rendered available without changing its source timestamp, then verifies the new off-route response coordinates/timestamp, keeps the exact trip row visible and requires no distance. No polling interval, timeout or accessibility assertion is relaxed. The structural race was identified in source; synthetic held-response execution is not a replay of the original failed CI trace.
