# Saved-trip schedule notices (#151)

Owner decisions: only saved trips; unread notices remain until dismissed. This is an in-app notice when a fresh official schedule is loaded, not a push notification or a live cancellation alert.

The first visit establishes a comparison baseline. A later official NJ Transit feed version is compared only for previously saved stop/route selections, including the app's existing paired return stops. New or reselected trips have no retrospective notice. Renaming or reordering a saved trip does not change its identity. Removed or reselected trips drop notices belonging to the old selection. No favorites or bus locks are modified.

The comparison uses the same calendar, pickup/drop-off, explicit arrival, after-midnight and DST rules as the timetable. Trip/pattern renumbering alone does not count as a bus change. Identical trip signatures are cancelled as multisets before expanding dates, preserving duplicate buses while keeping weekly comparisons small. Only common service dates are compared: a missing preceding day at a weekly file boundary must not look like a removed overnight bus. The comparison includes the last shared service day’s overnight departures and spring-forward service that starts on the preceding local evening. The first changed local day is shown with changed departures before and after; other dates may differ. No exact old/new bus identity or effective date outside those copies is guessed. Endpoint metadata changes and missing selected stops/routes get separate notices. If no future overlap can be compared, the app says so instead of claiming buses were cancelled. Calendar expansion is bounded to 367 days; comparison beyond that bound is explicitly unavailable.

Storage stays on this phone, in `dale-commute-changes-v1` in the browser Cache API, separately from existing favorites and the live schedule cache. One atomic entry per configured schedule source contains one canonical baseline, saved-trip identity keys and unread notices. It contains no GPS history, account token or raw live response. `/v1/local-commute-changes` is only a cache key, never a network request or a new Worker endpoint. Printed and demo sources do not use this feature. Clearing browser storage also clears the baseline and notices.

Operations are serialized within a tab and with Web Locks across tabs where supported. If Web Locks are missing or acquisition rejects before callback entry, operations use the in-tab queue in session-only mode: they can read the last baseline but never replace the shared durable record without a lock. An entered operation is never replayed. Each durable operation rereads the saved state under the lock, and schedule advancement also reads the current saved favorites rather than trusting a tab's older display snapshot. The existing source-scoped favorites storage is read only; this feature never writes it. A malformed payload, or a record rejected by the favorites loader, is not treated as intentional removal: the page becomes session-only and leaves durable notice history intact. Older built-at timestamps, offline loads, and favorite edits in an already-open older tab do not move the baseline backward. If notice storage or the saved-favorites read fails, the current page likewise stays session-only and warns that its changes cannot be safely saved after closing. It never resumes whole-state writes that could overwrite another tab's changes. Reloading creates a fresh store that can read current saved state again. No indefinite persistence can be promised when the browser removes storage.

Native details keep longer before/after lists closed initially; native buttons dismiss notices and return keyboard focus nearby. Notices sit after the existing commute cards, with no blocking popup, forced navigation or automatic expiry. English/Spanish, 12-hour clocks, five skins and enlarged narrow-phone text use existing app conventions.

Startup favorites are checked synchronously before the existing app's save effect can normalize a damaged value to an empty list. If that first snapshot is invalid, the notice store remains session-only even if the display loader subsequently saves its empty fallback. The separate durable notice history is preserved; this feature does not change how the pre-existing favorites loader or writer recovers favorites.

Verification uses fictional GTFS fixtures and intercepted API responses only. No Worker deployment, new backend access, live feed fetch, credentials, rider data or installed app is used. Independent Argon review is required because this feature persists local saved-trip identities. Actual iPhone/Safari, screen-reader and on-phone acceptance remain separate checks.
