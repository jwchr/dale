# Dale: development rules for Claude (the code still uses the old name `arriba` in places)

**Goal:** the most useful, trustworthy North Jersey to Manhattan NJ Transit bus app with the least engineering.
Read `docs/V1_CONTRACT.md` (what V1 is) and `docs/HANDOFF.md` (where things stand) at the start of every session and after compaction, then check the real state on GitHub. The 805-line master spec v1.3 is an archive; do not load it unless an issue links to a section of it.

## Product rules (owner decisions; see docs/DECISIONS.md)
- Household tool first (Jeff and one other household rider), built so it could go public later. No accounts in V1.
- Never invent live data. Every live bus, gate, zone or estimate carries its source and age; unknown is a valid answer. A bus that stops reporting is "not reporting", never "cancelled", unless NJ Transit says so.
- Exact-bus lock never switches buses silently (`src/domain/lock.ts`). Favorites keep the rider's order. A gate is never inferred from a route number.
- English and Spanish for every string (`src/ui/i18n.ts`); 12-hour times in both.
- Demo data must show the DEMO banner (`meta.demo`). Real data comes only from NJ Transit feeds via `scripts/build-gtfs.mjs` and the Worker; until M2 the printed-data exceptions are the owner-supplied route 165 timetable (D42, `scripts/build-timetable.mjs`) and the bounded supplied bus/rail documents authorized in D49 (#80; not yet published), which must keep printed-source attribution (D50 moves the persistent top notice into Settings → Data source).
- Independent app: never use NJ Transit or Port Authority logos as Dale's branding, or imply endorsement. Only exception (D69): the photographed real stop sign in "See bus stop sign" keeps its printed logos so riders can recognize it.

## Data and privacy
- D51/D52: bus credentials are verified (#87) and the owner requests the bounded live bus pilot (#89) on Cloudflare (Workers Paid since D85). Require verified exact trip/date matching, source age and explicit scheduled fallback; no archive, rail or shared-report access follows from this pilot. See docs/LIVE_BUS_PILOT.md.
- D60/#91 authorizes private indefinite history, background collection and actual agency cadence measurement; D77 expands archive scope to readable rail feeds; D84 makes raw bus and rail saving statewide again, replacing D83's four-county limit, with its own share of the daily write counter (Jeff, Nov 26, 2026: "It is absolutely critical. It is a P0 priority. Nothing is more important than getting this data saved... All the data, save all the data."; reason: NJ Transit feeds are live-only, so raw data missed while the write cap squeezed it out is lost for good). Jeff explicitly approved same-account R2 within Free usage; Project Control created private `dale-history`. Preserve original evidence/context; hot cleanup requires verified durable data+manifest readback. Enforce persistent storage/operation/write limits, no automatic paid overflow or new vendor. Independent HIGH review, separate release/activation and actual production evidence remain required. See docs/HISTORY_COLLECTION.md and docs/plans/2026-11-21-statewide-history.md.
- NJ Transit data terms apply (server-side storage, 40,000 requests/day per API, attribution, latency disclosure). The owner reported NJ Transit's OK for archiving on 2026-10-31; keep the archive private (scope: D83 above).
- This repository is public. Never commit NJ Transit credentials, tokens, recorded feed responses, rider locations or personal data. Credentials live only in repository or Cloudflare secrets set by the owner.

## Engineering
- **Never ship part of an approved feature, or move approved work to later, without Jeff's OK** (rules review, Jeff, Nov 26, 2026: "Yes, your picks"; reason: he decides what is in scope; how it looks is covered by the design check below and "Keep every app simple" in `~/.claude/CLAUDE.md`).
- **Design check for new visible features** (Jeff, Nov 24, 2026: "Yeah, that's a good idea."; reason: CodeRabbit and Neon review code, not how a screen looks, so a feature's look had no independent check). Before building anything that adds something new to a screen, put one screenshot of a rough version, made in the app, on Drive for Jeff, and build after his yes or his change: where a feature goes and how it looks is a product judgment only he can make (a new screen or layout change goes to him first under "Keep every app simple" in `~/.claude/CLAUDE.md`). Before the PR is ready, a fresh helper agent that never saw the code or the builder's reasoning reviews the real screenshots (390 px wide, English and Spanish, enlarged text, keyboard use) against the approved mock-ups for placement, hierarchy, spacing, touch targets, Spanish fit and contrast; fix its real findings and say in the PR what it found.
- Keep one web app (`src/`) and one Worker (`worker/`); no new packages until two real consumers exist.
- Domain logic is pure TypeScript in `src/domain/` with unit tests in `tests/unit/`; UI flows in `tests/e2e/` (Playwright, Pixel 7, pinned `?now=`).
- Use standard libraries (GTFS-Realtime bindings, MapLibre) over custom parsers when the need arrives; record license and version.

## How we work
Jeff's shared rules for every chat (permission, reviews and when a change is risky, PR limits, safety stops, spending, keeping the chat small, compaction at 60% instead of handoffs, SSOT) live only in `~/.claude/CLAUDE.md`, which Claude Code loads automatically. That file controls; do not copy its rules here, change them there. This section adds only Dale's own rules.

- **Plan checks go in a pull request.** Put a plan in `docs/plans/` on a docs-only PR, where CodeRabbit and Neon (in the ALL-open bundle) review it like code. Which PRs also go to Codex lives only in `~/.claude/CLAUDE.md` under Reviews (Jeff, Nov 26, 2026: a risky PR a Claude chat wrote gets one `@codex review` comment). Codex never answered `@codex` on issues here (no cloud environment; seen Nov 17 and Nov 19, 2026), so if it doesn't answer on a PR either, tell the Control Center.
- **Checks before merging.** `npm run verify` passes locally before every push, and the GitHub `test` check is green on the final commit. Docs-only pull requests (only `docs/**` or Markdown) do not start that check (D70); for them the local tests are the test requirement. Open pull requests as drafts while building. CI runs on pull requests and main only. (rules review, Jeff, Nov 26, 2026: "Yes, your picks"; reason: failures are caught before reviewers spend time).
- **CodeRabbit and Neon here.** Dale is public, so CodeRabbit is free here (Jeff, Nov 22, 2026). Every Dale pull request also goes to Neon in Dale's ALL-open bundle and merges only after both; that rule and its reason live only in `~/.claude/CLAUDE.md` under Reviews (Jeff, Nov 24, 2026, approving this pointer: "Yes, update it"; reason: the old line said CodeRabbit alone was the regular reviewer). CodeRabbit does not start by itself until `.coderabbit.yaml` turns auto review on; until then request it with one `@coderabbitai full review` comment when the pull request is ready. On a risky pull request its review is only an extra check.
- **Risky in Dale** also means Worker deploys, live-feed changes and history collection; they keep the conditions in `docs/LIVE_BUS_PILOT.md` and `docs/HISTORY_COLLECTION.md` (reason: a Worker change reaches riders at once, and history collection writes the private archive, which cannot be rebuilt if lost).
- **The builder merges.** When the checks pass, squash-merge, delete the branch, open the public Pages site and confirm the change on a narrow phone layout in English and Spanish, update `docs/HANDOFF.md`, and tell the owner in one or two plain sentences what changed and how to try it. (rules review, Jeff, Nov 26, 2026: "Yes, your picks"; reason: merging updates the live site, so problems show at once).
- **Short status file.** `docs/HANDOFF.md` holds only: what is built and live; what is waiting on the owner; what is next; known problems. Update it in place after every merge. No diary and no history. Ideas that are not approved work go to the owner's Idea Inbox. (rules review, Jeff, Nov 26, 2026: "Yes, your picks"; reason: every chat reads it at start, so short costs less).
